# Lemo 创意动画多协议与模型兼容性评估

日期：2026-11-03。范围：当前工作区源码的可行性与改造设计。本轮未修改生成链路、用户项目或模型配置，未调用付费模型。

## 结论

可以把现有创意动画改为支持 Chat Completions、Responses、Anthropic Messages 三种协议，允许使用各渠道的自定义模型。建议以“协议可插拔、能力按模型与渠道实测、阶段可以分配不同模型”为目标。

不能承诺所有模型都能可靠完成全片创作。协议决定消息如何传输；模型的代码生成、工具调用、图像理解、上下文与输出容量决定它能承担哪些工作。非视觉模型可以承担写代码，由另一个视觉模型负责审片；只有普通文本能力的模型可以评估受限生成模式，但不能沿用完整自动审片的通过标识。

当前阻断不是一个按钮问题，也不只是一个协议判断。仅删除 LEMO_SDK_PROTOCOL 检查，后续 SDK、网关和响应校验仍然要求 Messages 数据。

| 工具绑定 | creative-tools.ts 和 production-tools.ts 通过 SDK 的 tool/createSdkMcpServer 包装文件、图片、风格库、review_film、finish_film 操作 | 应先抽取通用工具处理器，再分别接 SDK 和原生协议；保留现有文件边界与宿主检查 |
| 请求与响应 | messages-gateway.ts 只接 /v1/messages，转发 Messages 请求；message-receipt.ts 校验 Anthropic JSON/SSE 生命周期 | 新增原生协议请求、响应和流结束验证；未知结果仍需保留账本状态 |
| 能力记录 | lemo-provider-capabilities.ts 的协议字段、判断及测试服务写死 anthropic | 改为按协议、端点、模型、配置指纹记录证据，不能复用另一渠道的通过结果 |
| 创作与交付 | lemo-upstream-graph.ts 的当前流程包含创意方案、素材、风格样片、旁白时间、整片创作、修复、渲染与验证 | 这些阶段与交付检查可以保留，不需要重做编辑器和媒体管线 |

关键边界：production-tools.ts 要求 review_film 返回真实图像后，至少再经历一个模型回合，才能 finish_film。现有完整自动流程包含图像审查；“API 返回了代码”不能直接当作合格成片。

## 两条可选路线

### 路线一：在现有 SDK 前面增加协议转换网关

SDK 继续发出 Messages 请求，由网关转换为 Chat Completions 或 Responses，再把结果转换为 SDK 可读的 Messages 响应。

优点是较多保留 SDK 的工具调度与恢复方式，适合范围明确、模型数量有限的兼容实验。

需要处理工具 ID、工具参数、工具结果、图片、并行调用、停止原因、流事件、Token 用量、上下文状态及 SDK 附加字段。各协议的推理状态、缓存与上下文压缩语义不一定能够无损对应；SDK 更新也会改变兼容面。当前网关直接保存与校验 Messages 原始回执，引入转换后还必须区分提供商原始回执与转换后的回执。

判断：可用于限定能力和指定模型的短期验证，不适合作为“任意模型都能运行”的产品承诺。不能通过改端点、删除字段或忽略工具结果让检测表面通过。

### 路线二：增加协议中立的创作执行层（推荐）

保留 Lemo 风格库、导演方法、工程约束、文件工具、真实抽帧、音频与 MP4 输出。增加宿主拥有的 Agent 调度器，使用各协议的原生请求和回执。

建议分为以下职责：

1. **统一会话表示**：文本、图像、工具声明、工具调用、工具结果、结束状态与用量。保留提供商原始回执和不可解释的续接信息，不能把全部内容压成文本字符串。
2. **原生协议适配器**：Chat Completions、Responses、Messages 各自编码、接收、校验；声明本渠道实际支持的能力。Responses 的 function_call/function_call_output 与 Chat 的 tool_calls/tool 消息不能用同一 JSON 结构直发。
3. **通用工具处理器**：复用已经有范围限制的读写文件、读图、读风格库、宿主渲染与结束验收；由宿主执行工具，模型只提出调用请求。
4. **受控循环**：请求模型、落盘回执、校验调用、执行工具、落盘结果、返回模型、继续创作。限制轮次与修复次数，并保留取消和未知结果的处理。
5. **持久化与恢复**：记录执行后端、协议、模型、配置指纹、适配器版本、会话与工具操作状态。已有官方 SDK 会话继续使用原执行器；新会话选用中立执行器。跨引擎切换从明确保存的阶段工件开始，不假装原会话可以直接 resume。

判断：初期工作量较大，但与“用户自行选择模型与协议”的长期目标相符。原 SDK 后端可以保留，降低一次替换全部流程的风险。

## 模型能力与产品行为

| 模型/渠道的实测能力 | 建议允许的用途 | 必须说明的边界 |
| --- | --- | --- |
| 稳定工具调用、图像理解、足够代码与上下文容量 | 完整创作、看图审查、修复、成片 | 成片仍以真实渲染和宿主检查为准 |
| 能写代码和调用工具，但不能理解图像 | 创意方案与代码创作，配合独立视觉审片模型 | 同一模型不能承担视觉审片；未配置审片模型时不能宣称该检查已完成 |
| 能稳定输出结构化文本，但没有原生工具调用 | 后续可研究宿主编排的受限生成流程 | 需要单独实现和验证，不在首轮承诺完整 Agent 等价能力 |
| 输出容易截断、代码/结构化结果不稳定或上下文不足 | 文案、局部辅助；或明确标为不适用 | 不能只因连接测试成功就允许完整自动制作 |

建议让用户配置“创作模型”和可选“审片模型”，默认允许同一个已验证模型兼任。不同阶段的模型配置在任务开始时固定；恢复时检查指纹，避免全局默认变化导致已运行任务中途换渠道。

首轮应将“完整流程”的能力门槛保留。是否允许非流式响应属于新执行器的设计选择；当前官方 SDK 路径要求的 SSE 不能直接取消。新执行器可以另行验证非流式模式，并在 UI 中明确它缺少实时文本输出，不能把协议传输特性一概当成模型创作能力。

## 改造顺序与完成标准

1. 抽取工具处理器、统一模型回合类型和执行器接口；保持现有 SDK 流程可运行。
2. 优先接 Chat Completions 与 Responses 的原生工具回合，再统一 Messages 的原生路径；每条路径使用独立回执测试。
3. 将协议白名单改为配置及能力检查，界面显示可创作、需独立审片模型、未验证或能力不足的具体原因。
4. 接入现有创意方案、样片、旁白时间锁、整片代码、抽帧修复与 MP4 交付；补齐事件与恢复存档版本。
5. 对每种协议验证工具往返、错误工具参数、图片结果、长代码输出、截断、取消、断线未知结果、崩溃恢复和预算消耗。最后以相同文案和风格做真实小样，人工比较叙事、排版、节奏、画面一致性及声音同步。

已有请求账本、受控工具和素材/渲染基础可以复用；不能直接复用普通文本请求的自动重试策略到有副作用的 Agent 流程。结果不明的请求要先核对，避免重复生成或重复计费。不同渠道的价格需要独立配置和证据，不能把 SDK 的美元估算机械套到所有模型。

这是执行层、能力检查与恢复格式的中等偏大改造。没有指定目标渠道、模型与验收预算前，不给出有保证的日期、成功率或费用。

## 本轮核查边界与资料

- 结论来自上述当前工作区文件的只读检查；未调整代码以绕过协议检查。
- 当前通用三协议调用不等于 Lemo 已有三协议 Agent 支持。
